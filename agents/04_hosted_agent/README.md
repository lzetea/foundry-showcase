# Scenario 04 — Foundry **hosted agent** (Contoso Travel concierge)

The same kind of containerized agent code as scenarios 02 (LangGraph) and 03
(multi-agent MAF) — but **Foundry builds and runs it for you**. You write the
agent, `azd deploy` it, and Foundry hosts the container on managed,
per-session-isolated infrastructure with a dedicated Microsoft Entra agent
identity. This is the counterpoint to the "bring your own Azure Container Apps"
model, and it exists to make the trade-off concrete.

## Hosted agent vs. container-on-ACA (scenarios 02 / 03)

| | **04 — Foundry hosted** | **02 / 03 — container on ACA** |
|---|---|---|
| Who runs the container | **Foundry** (managed) | **You** (Azure Container Apps) |
| Front door / auth | Foundry gateway + **Entra agent identity** (managed identity to the project) | **APIM AI Gateway** you provision + a subscription key you broker |
| Infra you own | none beyond the shared Foundry project | ACA environment, APIM, ingress, revisions |
| Model access | `FoundryChatClient` + `DefaultAzureCredential` — **no keys** | model calls routed through the APIM OpenAI route with a gateway key |
| Deploy | `azd deploy contoso-travel-hosted` (remote build in ACR) | `deploy_and_register.py` (ACR build + ACA revision + APIM wiring) |
| Scale-to-zero, session isolation, versioned rollouts, log stream | **built in** | you configure on ACA |

Same observability surface as every other scenario: it emits `gen_ai.*` traces
to Application Insights and is a first-class agent asset in the project, so the
shared `trace` / `evaluate` / `redteam` scripts target it unchanged.

## What the agent is

A single **Contoso Travel concierge** built with the Microsoft Agent Framework.
It calls three typed function tools over the Contoso inventory CSVs:

- `search_flights` — by origin, destination, cabin class, or max price.
- `search_hotels` — by city, star rating, max nightly price, or amenity.
- `search_car_rentals` — by city, car type, or max daily price.

The hosted runtime is `ResponsesHostServer(agent).run()` from
`agent_framework_foundry_hosting`, which serves the OpenAI-compatible **Responses
protocol** on port 8088 — exactly what Foundry (and `azd ai agent invoke`) calls.

## Files

| Path | Purpose |
|------|---------|
| `agent/main.py` | The agent: `FoundryChatClient` + `@tool` functions + `ResponsesHostServer`. Instructions + model come from `load_config()` so the Agent Optimizer can tune them. |
| `agent/agent.yaml` | The `ContainerAgent` spec (kind, name, Responses protocol **2.0.0**, env). See the in-file note on **not** setting `AZURE_EXPERIMENTAL_ENABLE_GENAI_TRACING`. |
| `agent/Dockerfile` | `python:3.12-slim` + `main.py` (remote-built in ACR) |
| `agent/requirements.txt` | `agent-framework-foundry`, `agent-framework-foundry-hosting`, `azure-ai-agentserver-optimization` |
| `agent/.agent_configs/baseline/` | Agent Optimizer baseline: `metadata.yaml` (model + temperature) + `instructions.md` (seed prompt) that `load_config()` reads at startup |
| `agent/instructions/concierge.md` | Human-editable system prompt (versioned, ASCII) that seeds the baseline |
| `agent/data/` | `flights.csv`, `hotels.csv`, `car_rentals.csv` the tools query |
| `eval.yaml` | Evaluation suite (dataset + evaluators) generated by `azd ai agent eval generate` |
| `scenario.py` | Adapter for the shared `trace` / `evaluate` / `redteam` scripts (calls the agent's own Responses endpoint with an Entra bearer token) |

## Deploy

The agent service is wired into the repo's `azure.yaml` (host type
`azure.ai.agent`). It reuses the **existing** Foundry project, so there is no
separate `azd provision` — install the `azd ai agent` extension once, then deploy
the code:

```powershell
cd demo-agent-observability
azd extension install azure.ai.agents   # once
azd deploy contoso-travel-hosted
```

The agent's Entra identity needs the **Azure AI User** role on the Foundry
account to reach the model; `azd deploy` wires this, but if the first invoke
returns an auth error, grant it and retry (RBAC propagation can lag).

`azd deploy` remote-builds the image in ACR, publishes a new immutable agent
version to Foundry, and prints the playground + Responses endpoint. Smoke-test it:

```powershell
azd ai agent invoke contoso-travel-hosted '{"input": "Find me a business-class flight from Seattle to Paris and a 4-star hotel with a gym."}'
```

## Optimize (Agent Optimizer)

The agent is wired for Foundry's **Agent Optimizer**: `main.py` loads its
instructions + model from `.agent_configs/baseline/` via `load_config()` (from
`azure-ai-agentserver-optimization`), so the optimizer can try candidate prompts
against an evaluation set without code changes.

```powershell
# 1. Generate an evaluation suite (dataset + evaluators) -> eval.yaml + .agent_configs/baseline/
azd ai agent eval generate

# 2. Score the current agent against it
azd ai agent eval run

# 3. Optimize: generate + score candidate prompts (gpt-5 reasoning, nano scoring)
azd ai agent optimize --optimize-model gpt-5 --eval-model gpt-5.4-nano

# 4. Review, then apply the winning candidate locally and redeploy
azd ai agent optimize apply --candidate <candidate-id>
azd deploy contoso-travel-hosted
```

`--optimize-model` must be an existing gpt-5-family (or DeepSeek) deployment in
the project. Applying a candidate rewrites
`.agent_configs/baseline/instructions.md`; `azd deploy` then rolls it out as a
new hosted version.

## Run locally (no deploy)

```powershell
cd agents/04_hosted_agent/agent
pip install -r requirements.txt
$env:AZURE_AI_PROJECT_ENDPOINT = "https://<account>.services.ai.azure.com/api/projects/<project>"
$env:AZURE_AI_MODEL_DEPLOYMENT_NAME = "gpt-5.4-nano"
python main.py   # serves the Responses protocol on http://localhost:8088
```
